# Project adoption and local governance

The entrypoint owns invocation and authorization. For first-time task work, use the scope section to build a map sufficient for that task, then follow relevant implementation and evidence. For an explicit full-governance request, cover the owned scope and apply the repair and verification sections. Targeted organization and acceptance cover the affected areas. Match depth to the request.

## Understand and cover the scope

Resolve the project from the user's target, effective instructions, manifests, and working context. A parent folder or Git ancestor is evidence, not automatic permission to govern every sibling. State the chosen root; ask only when plausible alternatives materially change the work.

Understand the purpose, responsibilities, active work, entry points, dependencies, and conventions relevant to the task. Identify active source roots, backups, generated/vendor trees, and the owner of current status before searching content. For full governance, inventory the owned structure and important documents, including areas missing from existing routes. Trace task-relevant behavior through implementation, callers, and test assertions. Inspect nested instructions before changing their scopes.

Exclude credentials, private originals, external/vendor trees, generated output, and unrelated areas unless this task specifically requires and authorizes them. Search task-relevant roots and file types first; when results are missing, check scope and ignore rules before widening. Include relevant Git-ignored source and documents explicitly. Narrow noisy or truncated results before reading more. Report exclusions and missing evidence; reading only existing routes is not a full pass.

## Shape the useful framework

Identify subject owners and their relationships. Preserve the established structure where it serves the work; shape a new area freely within its constraints, and change mature areas where evidence shows a concrete benefit.

Use [Node protocol](THUBAN-PROTOCOL.md) for node growth and startup. Repair the existing human-facing gateway so a person can see the major areas, important-file responsibilities, and how to begin work. Add missing material only when a recurring task lacks a suitable owner. Choose the number and kind of documents from the project; no standard directory tree or fixed file count is required.

## Repair directories and documents

Complete warranted local repairs under the request: stale instructions, broken references, duplicate active claims, confusing names, misplaced history, missing operating guidance, and inefficient gateways. Give each subject an authoritative location for current status and next actions; subprojects and modules may each own their states. Handoffs and task cards may keep brief summaries linked to that location. When status changes, synchronize affected summaries and label retained earlier states as history. Preserve plans as intent; verified behavior comes from implementation or its evidence set.

Before moving, merging, or retiring material, establish its unique useful content, consumers, path dependencies, and recovery. Check imports, build/tool configuration, scripts, links, and external consumers relevant to the move. Keep unknown dependencies unresolved rather than assuming a partial search proves there are none. Protected personal, signed, legal, or organization-authority records keep their original form unless the task explicitly includes changing them.

Use an available local recovery mechanism suitable for the changes. Git preserves only what it actually records; untracked/ignored files and private material need a local backup that respects their boundary. Preserve current uncommitted work. Change the owner and known consumers together. Retire redundant active documents after preserving unique content and recovery; archiving every obsolete duplicate can merely relocate clutter.

Explain the concrete local change set and why it helps, then execute within existing authorization. Continue verified independent repairs when one item requires a user decision. Additional authority is needed for a material expansion, conflicting ownership, or the reserved actions in the entrypoint—not for each consequence-equivalent file edit.

## Verify and finish

- **Structure:** node markers, parent tree, effective bootstrap, child reachability, and changed references resolve.
- **Meaning:** responsibilities and evidence owners remain coherent; preserved intent/history is distinguishable; important files and the human map match the actual project.
- **Operation:** run checks tied to changed paths or instructions, such as a build, import, command, or representative task. Check preserved unique content and the recovery copy.
- **Recovery:** after establishing project governance or making a substantial node/authority/organization change, use an independent agent when available and allowed. Give it only the permitted current artifacts and realistic tasks, with fresh context where possible. Exclude intended answers, implementation reports, suspected defects, and prior conclusions. Verify findings independently. First-time task exploration, ordinary maintenance, and read-only reviews do not need this pass.
- **Stability:** recheck the repaired conditions. A second unchanged pass should not create fresh nodes, duplicate summaries, churn wording, or update dates merely to record activity.

Report the result, significant changes, coverage and exclusions, verification, and remaining decisions. Independent recovery that was unavailable or used retained context must be described accurately. Keep detailed task evidence outside the project's live instruction surface unless an existing evidence owner needs it. A project that already meets its needs can finish with zero diff.
